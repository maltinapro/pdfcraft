# Roadmap

Derived from the business plan ("Businessplan PDFCraft", digitalrechnung.jetzt, sections 5 and 7) and checked against the current code. It lists only **code changes** that are worth doing now. Marketing, finance, legal and sales work is not part of it.

Status: `open` · `in progress` · `done`. After every finished epic or issue, update this file and the epic file. Conventions and GitHub workflow: [epics/README.md](epics/README.md).

GitHub issues are created **phase by phase** (epic issue + one sub-issue per task, labels `epic` / `task` / `phase-N`). Created so far: phase 1 (E01 #101, E02 #105, E03 #108), phase 2 (E04 #136, E05 #142), phase 3 (E06 #150) and phase 4 (E07 #160, E08 #166, E09 #175, E10 #180, E11 #184, E12 #190), each with its sub-issues.

## Current state (what already exists)

- Per-minute rate limits per token (`PAID_PLANS`), compile queue with load shedding, bulk limits per plan.
- Purchase page with renewal and cancelling, token info via `GET /v1/token`.
- Backup/restore page ("Daten & Sicherung") with reminder, archive, drafts, customer and article master data.
- PDF preview drawn with pdf.js (legacy build with polyfills, one shared worker) where the browser has no inline PDF viewer, e.g. Chrome on Android (#158, #159).
- Paper-first editor with four guided zones, clickable PDF navigation, resizable desktop panes, a Material Design 3 stepper wizard with mobile Form/Preview tabs and optional service/due dates; follow-up spacing, totals, scrollbar, mobile navigation and preview-outline fixes are documented in E08. The editor is a reusable package, `@maltinapro/editor` with a replaceable adapter ([README](../frontend/packages/editor/README.md), #221). The human five-task comparison against the E07-05 baseline and real-device checks remain open.
- Classic, Modern Minimal and Contrast designs for six document types, clearly different in the picker (E11) (DIN 5008), accent color, font, footer, logo, signature image.
- Landing page with meta tags and JSON-LD; Helm chart for the demo and the `/v1`-only production API (`values-production.yaml`: HPA, PDB, NetworkPolicy, ServiceMonitor, external Valkey; #224).
- E-invoice XML (EN 16931, XRechnung) generated by the backend, validated with Mustang in CI (E01: fixed corpus of invoices and credit notes).
- OpenAPI 3.1 spec `docs/openapi.yaml` for the document endpoints, linted in CI, examples tested against the backend, published at `/api/` (E02).

## Plan items deliberately not planned

| Plan item | Why not now | Build when |
| --- | --- | --- |
| Price change to 29 €/year and 3.90 €/month | Configuration only: `PAID_PRICES` (see "Pricing" in [12](12-paid-tokens-mollie.md)), no code | – |
| Monthly quotas (300 documents, 5,000 / 50,000 API calls) and usage display | Only a per-minute limit exists. The live preview uses the same token, so counting requests would punish editing, and the backend cannot tell preview from final download. Tiers can start without quotas: "API Growth" / "API Scale" and the "priority rate limit" map to the existing `PAID_PLANS` (`business` = 100/min, `pro` = 300/min) and `PAID_PRICES`, which is configuration only | API customers exist and one of them exceeds a fair monthly volume; then design a quota that counts final renders only |
| Token dashboard | The buy page already shows plan, per-minute limit, expiry, renewal and cancelling; only the monthly usage from the plan is missing, and it needs a quota | a quota exists |
| PAdES signatures | Not required for e-invoices ([15](15-pdf-signatures.md)); needs customer-owned signing certificates and key handling | a customer asks and brings a certificate |
| E2E-encrypted sync | The backup file already moves data; sync would put customer data on the server and breaks the privacy promise | repeated requests for multi-device use |
| Enterprise offer, custom template service | No lead yet; the production chart (`values-production.yaml`) already covers HA deployment of the API | a concrete enterprise or custom-template lead |
| Decision log, legal texts, purchase invoices, DPA, KPIs, license strategy | Not code. Open points are listed in `AGENTS.md` (steps 43, 45) | handled outside the repo; code only if a decision requires it |
| Developer test token, SDKs, Postman collection | Without evidence it is speculative; OpenAPI (E02) lets users generate clients | developers report the Anubis cookie as blocker |

## Claims in the plan to correct before they are published

- "Mustang validation integrated": done by E01 for a fixed corpus of invoices and credit notes in CI; the claim covers those documents, not every possible input.
- "Internetmarke with your own Portokasse" as a selling point: off by default, never verified against the live Deutsche Post API, and it is open whether partners may use end-customer Portokasse logins ([14](14-internetmarke-integration.md)). Do not advertise it before that is verified.
- "Pre-validated compliance certificate" for enterprise customers: no such certificate exists; the CI result from E01 is the most the project can show.
- "< 10 ms": true for typical documents (about 5 ms for 3 items, about 28 ms for 60 items); say "typically".
- "29 €/year and 3.90 €/month": the product launches at 24.00 € and 2.90 € (`PAID_PRICES`); the 29 € plan price and the finance figures are an owner decision, not a code task.
- The license is MIT (checked); a separate commercial module is not needed now.
- The finance plan's largest line (API customers) assumes the API tiers; they can be sold via `PAID_PLANS` without a monthly quota (see above).

## Recommended order

E01, E02 and E03 are independent and can run in parallel. E05 reuses the corpus from E01 and the page scaffold from E03-01. E04 can start any time. E06 only on demand.

Phase 4: E07 first (tokens, components, navigation; E07-05 records the usability baseline), then E08 (the core of the redesign; E08-08 adds service and due dates and can be done early) and E09; E10 can start after E07-01. E11 is independent and can run in parallel, but must keep the DIN zone positions that the E08 preview overlay relies on. E12 starts with its review report (E12-01); its tooling, dependency, backend and security issues can run in parallel to E07/E08, the frontend refactor (E12-06) waits for E08 and E09 so no work is spent on code the redesign replaces. Each issue is one PR; every phase-4 PR follows the playbook in the design guide (12.3) and, when it touches the preview, the device test matrix (12.2).

Suggested start: E07-05 (screenshot script and baseline) + E12-01 (review report) + E12-07 baseline, then E07-01 … E07-04.
